## Context

sandgit 工作流分为 6 个技能，第二个 `sg-test-branch-run` 承接 `sg-base-sync` 之后，负责测试沙箱的全生命周期：创建分支、编写测试、人工审核。审核通过后由 `sg-test-finalize` 合并入 main。

按照 README 规则：
- 沙箱内对开发环境内的代码读写权限全开，测试代码可自由编写和修改
- 合并时仅允许测试代码进入 main
- 测试标准必须经人工确认后方可入库

## Goals / Non-Goals

**Goals:**
- 从 main 创建 `sgtest/<name>` 分支作为测试沙箱
- 在沙箱中辅助用户编写测试文件
- 测试完成后进入人工审核环节，用户确认测试标准正确
- 审核通过后提示用户调用 `sg-test-finalize` 合并

**Non-Goals:**
- 不执行测试（只编写测试代码）
- 不合并到 main（由 sg-test-finalize 负责）
- 不修改 main 分支上的任何内容

## Decisions

1. **分支命名**：`sgtest/<描述>`，由用户输入简短描述作为分支名后缀。
   - 理由：`sgtest/` 前缀明确标识测试沙箱，与业务沙箱 `sgcode/` 区分。用户自定义后缀方便识别。
   - 替代方案（自动生成名称）：简单但缺乏语义，不便于管理。

2. **前置条件检查**：执行前确认当前在 main 分支。
   - 理由：测试沙箱必须从最新 main 创建，避免基于过时或错误基线。若用户未执行 sg-base-sync 先同步，提示先执行该技能。
   - 替代方案（自动从 main 切出）：可能使用户忽略前置 sync，风险自负。

3. **编写测试阶段**：AI 与用户协作编写测试代码，沙箱内无限制。
   - 理由：对齐 README "沙箱内对开发环境内的代码读写权限全开"，测试文件可随意增删改。

4. **结构化三步审核**：编写完成后不直接问"是否通过"，而是串行确认三项：① 测试覆盖说明（WHAT），② 测试方法说明（HOW），③ 静态用例验证（EVIDENCE）。每项可独立修订。
   - 理由：人工审核需要理解测试的意图、实现方式和正确性证据，三项串行确认避免信息过载。
   - 产出：一个需求对应一份测试文档，汇总覆盖范围、方法说明和验证结果。

## Risks / Trade-offs

- **风险**：用户跳过 sg-base-sync 直接从旧 main 创建沙箱 → **缓解**：检测当前分支，若非 main 提示先 sync
- **风险**：沙箱分支名冲突 → **缓解**：创建前检测分支是否已存在，若存在提示用户换名或复用
